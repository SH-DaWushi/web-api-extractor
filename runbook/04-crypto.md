# 模块 04-crypto · 步骤 5 · 加密与凭据核实（强制，禁止跳过）

> 主索引见 `SKILL.md`。**本步骤不可跳过**：无论 `crypto_found` 取什么值，都要先做完下面的
> 「必做核对」。**不是**「`crypto_found=true` 才读本模块」—— 区别只在于 `crypto_found=true`
> 时要额外读全本模块并调 `extract_crypto_logic` 看明细，`crypto_found=false` 时第 2–4 层
> 密文核实可以跳过（前提是必做核对已经通过，见下）。

> **硬规则：抓包中 JSON / 表单编码请求体里的凭据字段值被脱敏为 `***`，明文与密文在此不可区分。
> 禁止假设，必须核实。**（URL 与响应体**不**脱敏，别据此认定"抓到的一定是明文"。）

## 必做核对（`crypto_found` 取任何值都要做）

`crypto_found=false` **不等于「该站点不加密」**。脱敏边车只对**被遮蔽过**的值保留 `len`/`shape`；
若本轮抓包里根本没有凭据类请求，就没有任何形态元数据可供判定，这个 `false` 是**空的**
（不是「已核实为明文」）。所以先核对这一条：

- **本轮抓包是否真的覆盖了凭据交换？** 即抓包期间确实触发过一次登录 / 鉴权（发过带账号密码
  或凭据的请求），而不是直接复用旧的 `auth_state`、一个凭据请求都没抓到。
  可看的信号（来自 `analyze_traffic` 摘要）：目标 host 的 `auth_schemes` 是否给出 scheme 或
  凭据类 Cookie 名、相关端点是否标 `auth_required: true`。
- **若站点需要登录，却说不出任何凭据信号** → 本轮没覆盖登录，`crypto_found=false` **不构成
  结论**：要么补一轮（真正走一次登录再抓），要么如实告诉用户「本轮未覆盖凭据交换、因此未核实」。
- **若本轮确实覆盖了凭据交换、且 `crypto_found=false`** → 才能判定「本轮抓到的凭据字段没有
  命中密文形态 / 没有 URL 加密信号」，这是可下结论的 `false`，第 2–4 层核实可跳过。

> 无论哪种情况，`crypto_found=false` 都**只允许**得出「本轮无可核实的密文」这个结论，
> **不允许**得出「该站点的密码是明文传输」。

## 核实手段（`crypto_found=true` 时逐条做，按可靠性排序）

1. **URL 查询参数** — `encrypt=2` / `version=2` / `sign` 之类（最可靠信号）；
2. **形态元数据**（脱敏边车）— 保留了 `len`/`shape`：`shape` 为 `base64`/`hex` 且 `len >= 128`
   即可判为疑似密文（`shape` 是**严格分类**：先判严格十六进制、再判「像密文的 base64」，
   低熵退化串与 `password123` 这类普通 ASCII 都归 `plain`）。**不要拿某个固定长度去套**
   （如"RSA-2048 恒为 344 字符"）——不同算法与密钥长度给出的长度不同，用等号去否掉真密文会
   直接漏判；`len >= 128` 是**下限**，不是等号；
3. **前端 JS** — `crypto.subtle` / `JSEncrypt` / `CryptoJS` / `sm2` 调用与 PEM 公钥块；
4. **故意发一次明文请求看错误码** — 500（解密失败）vs 业务错误码（参数错）。

`analyze_traffic` 的 `crypto_found` 为 true 时调用 `extract_crypto_logic(session_id)` 查看明细。

> ⚠️ **不要假设「CDP 拿到的一定是明文」**。CDP 捕获的是网络层实际发出的字节，可能已被 JS 加密；加密后的值同样会被抓到（且按字段名脱敏后更难察觉）。按明文实现会撞 500。
